# 03 · The Internet checksum (ones'-complement sum)

## In one line
Add up the data as numbers, fold any carry back into the sum, flip every bit, and send that as the check value — the receiver adds everything including the checksum and expects all 1s.

## The problem it solves (real-life example)
A shop assistant totals your bill, writes the total at the bottom, and you re-add the column to check it. If one price was copied wrongly, your total differs. A checksum is that "total at the bottom" — cheap to compute, good at catching accidental slips. It is the same idea TCP and IP use for their headers.

## How it works

Steps (8-bit words, the textbook size; the protocol uses 16-bit words):
1. Split the data into *k*-bit words (pad the last word with zeros).
2. Add the words in binary. If the sum overflows *k* bits, take the carry that fell off the left end and **add it back on the right** (*end-around carry* / wrap-around).
3. Flip every bit of the result (ones' complement) → the **checksum**. Send data + checksum.
4. Receiver adds *all* words including the checksum with the same wrap-around. A clean message always gives `11…1` (the complement is 0). Anything else → error.

**Worked example, sender** (generated by `numericals.py`, which is unit-tested against `protocol.py`):

<!-- GEN:checksum8_sender -->
```text
Split the data into 8-bit words
  # The data is 16 bits long. We treat it as a list of 8-bit numbers.
  w1  10110011   <- 0xb3
  w2  01101100   <- 0x6c
Add word 2
  # Add word 2 to the first word. A carry fell out of the left end → wrap it around: add it back at the right.
  carries        11100000
  w1              10110011
  + w2            01101100
                 ---------
  sum            100011111
  carry out = 1  wrap around ↓
  carries        00011111
  sum (no carry)  00011111
  + carry 1       00000001
                 ---------
  sum            000100000
Sum of all words
  # The ones'-complement sum of the 2 words is 00100000.
  sum  00100000
Complement → checksum
  # Flip every bit of the sum (ones' complement). That is the checksum.
  sum       00100000
  checksum  11011111   <- 0xdf
Transmit data + checksum
  # The checksum is sent right after the data words.
  sent 10110011 01101100 11011111
```
<!-- /GEN -->

**Receiver, no error** → sum is all 1s → ACCEPT. **Receiver, bit 3 flipped in transit:**

<!-- GEN:checksum8_receiver_flip -->
```text
bit 3 of the data flipped in transit
Received words
  # The receiver splits what arrived into the same-sized words (the last one is the checksum). 1 bit(s) flipped in transit.
  w1        10100011
  w2        01101100
  checksum  11011111
Add word 2
  # Add word 2 to the first word. A carry fell out of the left end → wrap it around: add it back at the right.
  carries        11100000
  w1              10100011
  + w2            01101100
                 ---------
  sum            100001111
  carry out = 1  wrap around ↓
  carries        00001111
  sum (no carry)  00001111
  + carry 1       00000001
                 ---------
  sum            000010000
Add word 3
  # Add word 3 to the sum so far. No carry out of the left end, so nothing to wrap.
  carries     00010000
  running sum  00010000
  + w3         11011111
              ---------
  sum         011101111
Is the sum all 1s?
  # If nothing changed, data + checksum add up to all 1s (the complement is 0).
  sum         11101111
  complement  00010000
=> REJECT ✘ — the sum is not all 1s, so an error is detected.
```

### Why swapped words go undetected
Addition is commutative: `a + b = b + a`. If the network swaps two 16-bit words the *sum* does not change, so the checksum still matches. CRC32 treats the data as a polynomial where **position matters**, so it notices.

<!-- GEN:checksum_swap -->
```text
sent words      : 0x1111 0x2222 0x3333   (checksum 0x9999)
after swapping words 1 and 2 the receiver sees the same sum -> UNDETECTED
CRC-32 of the sent data     = 0x5e813fb2
CRC-32 of the received data = 0xfe5d8461   -> CRC DETECTS it
```
<!-- /GEN -->

The same effect on real bytes (what `python proxy.py --mode noise --pattern swap` does to a chunk):

<!-- GEN:swap_words_example -->
```text
before : 5365 6375 7265 5472 616e 7366 6572 204c 6162 2121
after  : 5365 7265 6375 5472 616e 7366 6572 204c 6162 2121   (words at bytes 2 and 4 swapped)
checksum16 before / after : 0xa536 / 0xa536
crc32      before / after : 0x825d13be / 0x58d0507a
```
<!-- /GEN -->

Other blind spots: two errors that cancel each other (+1 in one word, −1 in another), and added/removed zero words. And of course anyone who alters the data can simply recompute the checksum — it is **not** authentication.

Filter `tcp.port == 9000 && tcp.len > 0`. In a checksum-mode frame the FLAGS byte (offset 4) has bit 2 set (`04`) and the first two bytes of the CHECK field (offsets 13–14) are `00 00`.

## Limitations
Misses reordered words and compensating errors; only 16 bits, so roughly 1 random corruption in 65 536 slips through; no protection against a deliberate attacker.

## Likely viva questions
1. **Why is the result complemented?** So the receiver can add everything including the checksum and test for all 1s — and so a zero-filled message is distinguishable from an erased one.
2. **What is end-around carry?** A carry out of the top bit is added back to the bottom, making the arithmetic ones'-complement instead of modulo 2^k, so the carry information isn't lost.
3. **Give an error a checksum misses.** Swapping two 16-bit words: the sum is unchanged. CRC32 catches it because it is position-sensitive.
