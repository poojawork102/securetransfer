# 01 · TCP sockets and the client–server model

## In one line
TCP gives two programs a reliable, ordered stream of bytes; our client sends the file over that stream as numbered frames and our server checks and saves them — but TCP alone cannot tell us the file is *right*.

## The problem it solves (real-life example)
You email a photo to a friend. You don't care *how* the bytes get across the internet, only that the same photo arrives. TCP is the postal service that numbers every packet, re-sends lost ones and delivers them in order. The client–server model says who plays which role: the **server** waits at a known address and port; the **client** connects to it and asks for service.

## How it works

```
 CLIENT                                   SERVER
   │                                         │  socket(); bind(:9000); listen()
   │── SYN ─────────────────────────────────▶│  accept() blocks here
   │◀─────────────────────── SYN + ACK ─────│     (the 3-way handshake:
   │── ACK ─────────────────────────────────▶│      both sides agree to talk)
   │  connect() returns                      │  accept() returns a new socket
   │══ sendall(frame) ═══════════════════════▶│  recv() ...
   │◀═══════════════════════ sendall(reply) ══│
   │── FIN ... ─────────────────────────────▶│  connection closed
```

1. **Server**: `bind()` to a port, `listen()`, then `accept()` each client on its own thread (`server.py`).
2. **Client**: `create_connection(host, port)` performs the handshake (`client.py`).
3. **TCP is a byte stream, not a message stream.** Ten `sendall()` calls may arrive as one `recv()`. So our protocol needs *framing*: a fixed 17-byte header that says how long the payload is, and `recv_exact(n)` which loops until exactly `n` bytes have arrived (`protocol.py`).
4. In our setup the client does not talk to the server directly. It connects to the **proxy on :8000**, which opens a second TCP connection to the **server on :9000**. Each leg is a normal, perfect TCP connection — the proxy is where we inject faults.

### Why TCP alone isn't enough
* TCP's checksum is only 16 bits, covers one segment, and is recomputed by every router that rewrites headers (NAT) — it does not protect data inside a middlebox, a buffer or on disk.
* Corruption that happens *above* TCP (in our proxy, in an application bug, on the storage layer) is delivered perfectly: TCP faithfully delivers the wrong bytes.
* TCP has no idea who wrote the bytes. Anyone on the path who can change the data can also fix up the checksum.

So the application adds its own **per-chunk check** (checksum / CRC32 / Hamming / HMAC) and an **end-to-end SHA-256**. The next documents explain each.

## Limitations
* One TCP connection per file; no resume after a dropped connection (the server quarantines the partial file instead).
* TCP gives no confidentiality — anyone on the path can read the frames.

## Likely viva questions
1. **Why do you need your own framing if TCP is reliable?** TCP is a byte stream with no message boundaries; the header's LEN field tells the receiver where each frame ends.
2. **What does the 3-way handshake do?** It synchronises initial sequence numbers and confirms both sides can send and receive before any data flows (SYN → SYN+ACK → ACK).
3. **If TCP already checks for errors, why did you add CRC32?** TCP's 16-bit checksum is weak and only protects the transport hop; corruption above TCP or by a middlebox is delivered as if it were correct, and nothing in TCP stops a deliberate attacker.
