# 04 · CRC — error detection by polynomial division

## In one line
Treat the data as one huge binary number (a polynomial), divide it by a fixed generator using XOR instead of subtraction, and send the remainder; the receiver divides again and expects remainder 0.

## The problem it solves (real-life example)
A barcode's last digit is computed from the others, so a scanner can notice a misread. A CRC is a far stronger "last digit": it is designed so that the typical damage on a wire — a flipped bit, or a short *burst* of garbled bits — always changes the remainder.

## How it works
1. Choose a **generator** polynomial *G* of degree *r*, e.g. `1011` = x³ + x + 1 (so r = 3).
2. Append *r* zeros to the data.
3. Do **modulo-2 long division** by *G*: if the leftmost bit of the window is 1, XOR with *G*; if 0, XOR with zeros; drop the leading bit, bring down the next. No borrows, no carries.
4. The *r*-bit remainder is the CRC. Send data + CRC.
5. Receiver divides the whole received codeword by *G*. Remainder 0 → accept; non-zero → error.

### CRC-32, the one in our frames
CRC-32 (IEEE 802.3) uses a 33-bit generator and three conventions on top of plain division — reflect each byte, preset the register to all ones, reflect and invert the result. It produces 32 bits per chunk (`zlib.crc32`, stored in the CHECK field).

<!-- GEN:crc32_example -->
```text
data                   = b'HELLO'
reflect + preset + 32 zeros -> 72-bit dividend
remainder (33-bit division)  = 10010011110110011101110101111100
reflect + invert             = 0xc1446436
zlib.crc32                   = 0xc1446436
our frame header CHECK field = 0xc1446436
```
<!-- /GEN -->

### What CRC detects — and what it doesn't
* ✅ every 1- and 2-bit error in a chunk, and every **burst** of up to 32 bits; other corruption slips through with probability about 2⁻³².
* ❌ **Not deliberate tampering.** There is no secret in a CRC: an attacker who rewrites the data just recomputes it. Our proxy's *attack* mode does exactly that (see doc 06).
* ❌ It cannot *repair* anything by itself — the answer to a CRC failure is a NACK and a re-send.
* An error pattern that is itself a multiple of the generator is invisible (the Lab shows an example).

CRC is computed on the **plaintext, before Hamming encoding**, so it also verifies the result of FEC: if Hamming mis-corrects a 2-bit error, the CRC still fails.

## Wireshark evidence
Bytes 13–16 of each frame (the CHECK field) change with the payload. In *attack* mode compare the same SEQ on `tcp.port == 8000` and `== 9000`: the payload contains `HACKED!!` **and the CRC bytes differ** — the attacker recomputed them, which is why the server's CRC check passes.

## Limitations
No security; no correction; the 32-bit size means a 2⁻³² chance that random damage goes unseen.

## Likely viva questions
1. **Why XOR instead of subtraction?** Polynomial arithmetic over GF(2): addition and subtraction are both XOR, so division needs no borrows and is cheap in hardware.
2. **Why is CRC better than a checksum?** The remainder depends on the *position* of every bit, so reordering is caught, and the generator is chosen to catch all short bursts.
3. **If CRC is so good, why do we also need HMAC?** CRC defends against accidents, not adversaries — anyone can recompute it.
